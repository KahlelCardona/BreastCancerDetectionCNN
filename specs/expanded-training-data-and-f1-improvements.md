## Purpose / Big Picture

Today, training only uses 2,864 of the repository's 10,237 mammogram images (from `data/raw/csv/mass_case_description_train_set.csv` and `calc_case_description_train_set.csv`), and both models' F1 score (a single number combining precision — how many of a model's "Malignant" calls were correct — and recall — how many of the truly malignant images a model actually caught — into one score that rewards a model for being good at both, not just one) sits in the mid-60s: 0.6534 for ResNet, 0.6375 for EfficientNet, as measured honestly on images neither model has ever seen. After this plan, three concrete, independently-measured changes will have been applied, and this document will report, honestly, how much each one moved the needle: first, roughly 2,800 additional real photographic images — cropped, zoomed-in patches of the exact same findings already in the training data, currently sitting completely unused on disk — will be added to training, which should give both models more to learn from without touching the 704-image test set at all. Second, each model's decision threshold (the cutoff on its own confidence score that decides "Benign" vs "Malignant," fixed at the midpoint of 50% today) will be tuned to the value that actually maximizes F1 on validation data, rather than assumed. Third, instead of picking one "best" checkpoint per architecture out of the five produced by 5-fold cross-validation (cross-validation is a technique that trains five separate copies of a model, each holding out a different fifth of the training data to validate on, so you get five independent estimates of quality), all five will be combined into a single averaged prediction per architecture, a well-established technique (called ensembling) for improving reliability without any new data or retraining.

Concretely, after this plan: running `py evaluate.py --model resnet --checkpoint checkpoints_resnet/fold1_best.pth checkpoints_resnet/fold2_best.pth checkpoints_resnet/fold3_best.pth checkpoints_resnet/fold4_best.pth checkpoints_resnet/fold5_best.pth --tta --threshold 0.42` (the exact threshold will be whatever Milestone 1 measures, not necessarily 0.42) will print an accuracy/precision/recall/F1 line for the 5-checkpoint ensemble on the same 704-image held-out test set used throughout this project, and that F1 number is expected — though, consistent with how this whole project has operated, not guaranteed — to be higher than today's 0.6534/0.6375 baseline. The web app (`py app.py`) will keep working exactly as a user already knows it (upload an image, see ResNet's verdict, EfficientNet's verdict, and a blended Final Answer), but internally it will be using whichever combination of these three techniques is empirically shown, in this plan's own measurements, to produce the best held-out F1 for each architecture.

A fourth, later-added change (see the second Approval entry above) makes every epoch's and every fold's training results additionally visible in Excel, not just in terminal output: after `py ResNet.py` or `py EfficientNet.py` finishes (or even while it is still running, since the file is saved after every epoch), opening `training_logs/resnet_training_log.xlsx` or `training_logs/efficientnet_training_log.xlsx` in Excel shows an "Epochs" sheet with one row per fold/epoch (train loss, validation loss, validation accuracy, precision, recall, and F1) and a "Fold Summary" sheet with one row per fold (that fold's best validation F1, its TTA-evaluated F1, and its tuned decision threshold), so the same numbers currently only visible by scrolling back through terminal output become a plain spreadsheet a person can sort, chart, or share.

- Observation: `ResNet.py`'s configuration (`CFG`) was edited outside of any ExecPlan process between the completion of the prior plan and the start of this one: `EPOCHS` changed from 40 to 55, `EARLY_STOP_PATIENCE` from 10 to 12, `T_0` (the cosine-annealing restart period) from 10 to 15, and `SAM_RHO` (the SAM optimizer's neighborhood size) from 0.05 to 0.07. This plan treats those as the current, intentional state of the file and does not revert them; Milestone 2's ResNet retrain will use these values, not the ones recorded in the prior plan.
  Evidence: a file-change notice during this session showed the diff directly; the file was not touched by any command in this plan or its predecessor.
- Observation: of the 10,237 total JPEG images, 3,311 sit in folders containing exactly one image (the full mammogram used by every CSV row today, matched via the `"image file path"` column), and 3,463 sit in folders containing exactly two images each (6,926 images total) — a cropped diagnostic patch and a full-resolution ROI (region of interest) mask marking the lesion's boundary, for the same findings already present in the training and test CSVs, not new patients or cases.
  Evidence: `Path('data/raw/jpeg').iterdir()` grouped by file count per folder gave exactly `{2: 3463, 1: 3311}`, and `3311*1 + 3463*2 == 10237` exactly.
- Observation: within each two-image folder, the file that is the real cropped photograph versus the file that is the ROI mask cannot be told apart by filename. The CSV's `"cropped image file path"` and `"ROI mask file path"` columns both resolve to the same folder (they differ only in the final DICOM frame number, `000000.dcm` vs `000001.dcm`), and which frame number becomes which converted JPEG is not consistent: testing 150 random two-image folders found 22 (14.7%) where the file named `"1-*.jpg"` was actually the mask and `"2-*.jpg"` was the real crop — the reverse of the naive assumption.
  Evidence: printed per-file grayscale statistics for the 150-folder sample; 22 folders had the `"1-*.jpg"` file with a large full-mammogram-scale resolution and fewer than 20 distinct grayscale values (mask-like) while the `"2-*.jpg"` file was small with 200+ distinct values (crop-like).
- Observation: pixel-content statistics, specifically the count of distinct grayscale values in the image, reliably separate the two files in every single one of the 3,463 two-image folders with zero exceptions: the real cropped patch always has more than 100 distinct grayscale values (typically 200-256, since it is a real photographic crop with natural tissue texture), while the ROI mask always has fewer than 20 (since it is a near-binary shape outline). An initial pass that also required the mask candidate to have a low average brightness flagged 73 folders as "ambiguous," but re-checking those 73 by distinct-value-count alone showed the same clean separation (14-16 distinct values on the mask side, 238-256 on the crop side in every case) — the average-brightness check was simply unnecessary and too strict, not evidence of real ambiguity.
  Evidence: a full scan of all 3,463 two-image folders reported "Clean (exactly one crop-like + one mask-like): 3390, Ambiguous: 73," and manual inspection of all 73 "ambiguous" rows showed each one still had one file with under 20 distinct values and the other with over 230.
  Implication for Milestone 2: the rule this plan uses to pick the crop out of a two-image folder is "the file with more than 100 distinct grayscale values," full stop — no brightness check, no reliance on filename or on which CSV column pointed to it.
- Observation: all 2,864 rows across `mass_case_description_train_set.csv` and `calc_case_description_train_set.csv` (100% of both files) have a non-null value in both the `"cropped image file path"` and `"ROI mask file path"` columns, meaning essentially every training row is a candidate for the crop-augmentation in Milestone 2, not just some subset.
  Evidence: `df['cropped image file path'].notna().sum()` and the equivalent for the ROI mask column both equal `len(df)` for both CSV files.

- ResNet: fold1=0.37 (val F1 0.7227), fold2=0.45 (0.7505), fold3=0.44 (0.7310), fold4=0.41 (0.7517), fold5=0.44 (0.7302). Average: 0.4220.
- EfficientNet: fold1=0.35 (0.7295), fold2=0.31 (0.7143), fold3=0.42 (0.7372), fold4=0.23 (0.7199), fold5=0.47 (0.7379). Average: 0.3560.

A plausible explanation, offered here as informed speculation rather than something this plan tested: cropped patches are close-up, zoomed-in views of the same lesion whose corresponding full mammogram is also in the training set, so they may teach the model to recognize the same specific lesions' local texture more confidently (raising validation F1, which is measured on data drawn from the same distribution and often literally related images) without teaching it to generalize better to entirely new, unseen cases in the held-out test set — the validation-vs-test optimism gap noted back in Milestone 1 (val F1 in the 0.71-0.75 range vs. test F1 in the 0.55-0.65 range throughout this entire plan) is consistent with this, and if anything widened slightly after augmentation. A future plan revisiting this could try validating that theory directly, or explore other ways to increase effective training-data diversity (e.g. stronger geometric/photometric augmentation of the existing full images, rather than adding real but closely-related crops) instead of assuming more real images necessarily means better generalization.

## Idempotence and Recovery

`evaluate.py`'s new ensemble/threshold code paths are read-only with respect to the dataset and checkpoints, exactly like its existing single-checkpoint path; re-running any evaluation is always safe. Re-running `py ResNet.py` or `py EfficientNet.py` overwrites their own checkpoints in place, exactly as established in the prior plan, and neither script supports resuming a partially-completed fold; an interrupted run should be restarted from the beginning rather than trusted partially. `training_logs/resnet_training_log.xlsx` and `training_logs/efficientnet_training_log.xlsx` are overwritten from scratch at the start of every `py ResNet.py`/`py EfficientNet.py` run (per the Decision Log above), exactly mirroring that run's own checkpoint-overwrite behavior; there is no need to delete them between runs, and an interrupted run simply leaves behind a partial, still-valid, still-openable spreadsheet covering whatever folds/epochs completed before the interruption.

`inference.py`'s and `app.py`'s behavior is entirely determined by the contents of `eval_results/selected_models.json` at the moment `load_selected_models` runs, so updating that JSON file and restarting `py app.py` is always a safe, reversible way to change which combination the web app uses; keeping a copy of the prior plan's original `{"resnet": {"checkpoint": "checkpoints_resnet/fold1_best.pth", "accuracy": 0.6776}, "efficientnet": {"checkpoint": "checkpoints_efficientnet/best_model_fold_2.pth", "accuracy": 0.6705}}` (reproduced here in full for exactly this purpose) provides an easy manual rollback to the pre-this-plan configuration if the new selections ever need to be reverted, though the underlying checkpoint files themselves are overwritten by Milestone 2's retrain and cannot be recovered once that runs.
